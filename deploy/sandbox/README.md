# Sandbox deployment

Publishes the three front ends as a single app on the NEXUS sandbox, for
demonstrating the Privacy Portal without its backend services.

```bash
./deploy/sandbox/build-and-publish.sh            # build and publish
./deploy/sandbox/build-and-publish.sh --build    # build only, leave it staged
```

The app answers at `https://privacy-portal-edson.sandbox.aim.int.gov.ab.ca`:

| Path | App |
|---|---|
| `/` | redirects to the privacy features page |
| `/complaints/` | complaints, including the account pages and the inbox |
| `/account-history/` | services accessed |
| `/admin/` | admin |

**A newly published app is unreachable until it is registered on the gateway**
at <https://apps.sandbox.aim.int.gov.ab.ca>. That step is manual. A blank page
on the sandbox URL is far more often an unregistered app than a broken build.

## Why one app rather than three

Each front end was published separately to begin with. Three apps meant three
URLs, three gateway registrations, and cross-app links that could not work,
because `NX_PUBLIC_COMPLAINTS_BASE_HREF` and the side menu both assume the
apps share a host. Serving them from one nginx container behind path prefixes
fixes the links and leaves one thing to register.

## Files

| File | What it is |
|---|---|
| `build-and-publish.sh` | Applies the env overrides, builds, assembles the site, publishes |
| `Dockerfile` | `nginx:alpine` on port 8080, as Cloud Run requires |
| `nginx.conf` | Path prefixes, per-app SPA fallback, cache headers |
| `env/*.env` | Sandbox environment overrides, copied to `.env.local` at build time |

`.staging/` is generated by the script and is not tracked.

## Two settings that are not optional

**`absolute_redirect off`.** Without it nginx puts its own host and port in a
`Location` header, so the redirect from `/` becomes
`http://localhost:8080/complaints/features` — a dead address once the app is
behind the gateway.

**`Cache-Control` on HTML.** Asset filenames carry a content hash and every
build deletes the previous ones, but `index.html` is not hashed. With no
cache-control header a browser caches the document heuristically, then asks for
a script that no longer exists, gets a 404, and renders **a blank page with no
error in the console**. HTML is `no-store`; hashed assets are `immutable` for a
year.

## Demo mode

`NX_PUBLIC_DEMO_MODE=true` in every env file here. It is off unless the value
is exactly `true`, so dev, syst, uat and prod builds are unaffected. When on:

- a signed-in demo user stands in for UIAM, which satisfies `SignedInOnly` and
  supplies the side menu
- the API layer answers a set of endpoints from `shared/src/lib/api/demoData.ts`
  and stops redirecting to the error page when a request fails
- complaint submission, email and document upload are acknowledged rather than
  performed

Nothing submitted in a sandbox build is saved anywhere. It should not be put in
front of anyone who might take it for the real service.

## What the demonstration contains

Twelve pages, reached from the left navigation, listed with their routes in the
repository's root README. Two are worth describing here.

The **citizen-facing experience** at `/account-history/transparency` is an
access log: who in government looked at the holder's personal information,
what they saw, and the reason they gave for looking. Its fields follow "Access
to Citizen Personal Information - Audit and Disclosure Log, Field Reference"
(19 September 2026) - the five of its Part 1 in the table, the Part 2
inventory on each record. Its categories are the topics Alberta.ca groups its
services under, taken verbatim from the published services inventory, and
every access is filed under one of them. No individual who accessed the
information is named, in full or as initials: an access identifies a position,
a position ID and a program area, and a review identifies the body that
carried it out.

The **Alberta Wallet** at `/complaints/alberta-wallet` groups its cards under
the same service topics. Each card opens the website of the service it belongs
to, in a new tab.

## Design system

Colours, spacing, type, borders and radii come from the design system's own
tokens. Four specs enforce that rather than leaving it to memory:

- `shared/src/style/designSystemConformance.spec.ts` refuses a literal colour,
  a raw font weight or size, a hand-set line height, a colour property set to
  `none`, and overriding the line height a `--goa-typography-*` token carries
- `shared/src/style/designTokens.spec.ts` refuses a reference to a `--goa-*`
  token nothing defines
- `shared/src/lib/style/palette.spec.ts` keeps the few hard-coded colours - for
  attributes a CSS variable cannot reach - matching the tokens they mirror
- `shared/src/lib/app-header/accountMenu.spec.ts` keeps the account menu from
  painting a link the colour of its own text

All four read `@abgov/web-components/index.css`, not `@abgov/design-tokens`,
because that is the stylesheet the apps import and the two do not always agree.

`shared/src/style/overrides.css` lists every token this deployment still sets
for itself, each with its reason. Two are deliberate departures: the side menu
is one `space-xl` wider than the design system's 256px, so the inbox entry's
second name fits beside its heading, and the callout's text is not inset.

## Upgrading the design system

The `design-system-2` branch moves the four `@abgov` packages to their 2.x
line. It compiles, passes, and serves every route. It is parked:
`@abgov/design-tokens` 2.12.8 puts greyscale-black at `#000000` where
design.alberta.ca publishes `#333333`, info-default at `#0077ad` against
`#004a8f`, and doubles the radius scale. Merging it would move this deployment
away from the published design system. Revisit when the site publishes those
values.

## What cannot be checked here

There is no browser in the sandbox. Chromium is installed but refuses to start
outside a snap cgroup, so anything visual is verified as compiled CSS, as
served HTTP, or by measuring text from the brand font's own metrics - not by
looking at it. Whoever is reviewing a change to layout or type is the only one
who can see it.

## What is not deployed

The six .NET services under `backend/`, and with them all business logic,
persistence and document handling. Each project references
`backend/src/Libs/Libs.csproj`, which pulls private `GoA.*` and
`UiamRpClientLib` packages from `nuget.pkg.github.com/GovAlta-EMU`, so building
one needs a token with `read:packages` for that organisation. Their Dockerfiles
also expect build arguments and the repository root as build context, neither
of which `publish-app` provides, and at runtime they need Cosmos DB, Key Vault,
Blob Storage and UIAM. Running them here is a porting exercise, not a
deployment.

## Placeholder content

Names, addresses, identifiers, health and banking numbers, and reference
numbers in the demo data are invented. The Alberta wordmark on the wallet card,
the shield of arms, the Interac Verified mark and the app store badges are
stand-ins drawn from type or the design system rather than the official assets;
replace them when those are available.
